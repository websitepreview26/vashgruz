# Приём заявок и фото: Cloudflare Workers → Telegram

Интерфейс остаётся на GitHub Pages. Worker принимает `POST /api/orders` (multipart/form-data), проверяет подпись Telegram, сохраняет заявку в D1 и отправляет текст и до 5 фото в заданный чат. Токен находится только в секретах Worker. Самостоятельного постоянного хранилища снимков нет: после загрузки Telegram сохраняются его `file_id`.

## Текущее подключение

Рабочий бот `@vash_gruz_by_bot` подключён к отдельному окружению:

- Конфигурация: `backend/wrangler.production.jsonc`.
- Worker: `https://vashgruz-production-api.vashgruz-api.workers.dev`.
- База: `vashgruz-production-orders`; все миграции применены, тестовые заявки не переносились.
- Скрытое подключение токена, выбор группы и настройка webhook: `./connect-production-telegram.command` из корня проекта. Рабочий бот должен быть администратором закрытой группы. Помощник проверяет username, отдельные Worker/базу, а также отсутствие чужого webhook до сохранения секретов. Кнопка меню «Получить оценку» настраивается автоматически через Telegram API.

Интерфейс использует рабочий API из `api-config.js`. Токен нового бота и группа сохранены в секретах рабочего Worker; webhook подтверждён Telegram. Локальные заявки и телефоны разделены по Telegram ID и адресу API. Для повторного подключения вручную: `python3 backend/tools/connect_telegram.py --config wrangler.production.jsonc`, затем `python3 backend/tools/enable_statuses.py --config wrangler.production.jsonc`. Без `--config` инструменты продолжают работать с тестовым окружением.

Обновление рабочего окружения из `backend/`: `npm run migrate:production`, затем `npm run deploy:production`. Конфигурация и база тестового окружения сохранены отдельно; обычные `npm run migrate` и `npm run deploy` продолжают использовать их. Общий опубликованный интерфейс теперь предназначен для рабочего бота; старый тестовый бот не может авторизоваться на рабочем API.

Тестовый Worker сохранён: `https://vashgruz-api.vashgruz-api.workers.dev`.
База D1 создана, миграция применена. Для проекта используется отдельный профиль Wrangler `vashgruz`, активированный в каталоге `backend/`. Входы других проектов не меняются.

Для подключения тестового `@vash_gruz_test_bot` запустите из корня проекта в обычном терминале:

```sh
./connect-telegram.command
```

Помощник скрыто запросит токен, проверит бота и аккаунт Cloudflare, найдёт группы в обновлениях Telegram и после выбора получателя сохранит `BOT_TOKEN` и `TELEGRAM_CHAT_ID` через stdin Wrangler. Токен не выводится и не сохраняется в файл. Если подключён свой webhook, ID группы запрашивается вручную; при чужом webhook настройка останавливается до изменения секретов. Настройка не отправляет сообщений в группу.

Бот и группа подключены через секреты Cloudflare. URL Worker указан в `api-config.js`; опубликованный интерфейс отправляет реальные заявки при запуске через Telegram. Для локального просмотра без подписанных данных Telegram отправка недоступна.

## Что создать

1. Аккаунт Cloudflare. Если на компьютере уже был вход в другой аккаунт, явно выбрать новый аккаунт при `wrangler login` и проверить `wrangler whoami` перед созданием ресурсов.
2. Бот через официальный `@BotFather`, команда `/newbot`. В настройках Mini App указать `https://websitepreview26.github.io/vashgruz/`. Запускать из кнопки меню/профиля, чтобы Telegram передавал подписанные `initData` с пользователем.
3. Закрытая группа для заказов. Добавить бота и разрешить ему отправку сообщений, фото и альбомов. Для личного чата получатель должен сначала нажать Start у бота.

## Развёртывание

Нужен Node.js 24+. Команды выполнять из `backend/`:

```sh
npm install
npx wrangler login
npx wrangler whoami
npx wrangler d1 create vashgruz-orders
```

Подставить полученный `database_id` в `wrangler.jsonc`. При нескольких аккаунтах добавить в конфигурацию `account_id` нужного аккаунта.

```sh
npm run migrate
npx wrangler secret put BOT_TOKEN
npx wrangler secret put TELEGRAM_CHAT_ID
npm run deploy
```

Значения вводятся в скрытом запросе CLI. **Не вставлять токен в index.html, api-config.js, команды, коммиты или переписку.** ID группы можно посмотреть в обновлении `message.chat.id` через Telegram API `getUpdates` (только если у бота не установлен webhook). При существующем обработчике не сбрасывать его webhook ради получения ID; прочитать ID через этот обработчик.

После публикации проверить `https://<имя-worker>.<поддомен>.workers.dev/health`: `configured` должен быть `true`. В корневом `api-config.js` указать этот URL в `apiBase` (без `/api/orders`), затем опубликовать интерфейс. Без URL приложение остаётся в демо-режиме и никуда не отправляет данные.

## Проверка с телефона

В собственном тестовом боте и группе отправить заявку без фото, с одним фото и с несколькими. Проверить: первое фото приходит с подписью заявки и кнопками, остальные снимки приходят ответом на него; повторное нажатие не создаёт вторую заявку; успех отображается после получения ответа API. Загрузка с `file://` предназначена только для локального демо – реальная отправка разрешена с указанного GitHub Pages origin и с проверенными initData.

Для старых альбомов отдельная карточка управления доставляется через `delivery_outbox`. После подтверждения её ID сохраняется как рабочий `message_id` заявки. Ежеминутная задача восстанавливает управление ранее отправленными альбомами без повторной отправки фото. При потере ответа Telegram автоматического повтора нет; для ручного подтверждения через `resolve_notification` требуется `messageId` существующей карточки. Новая миграция не требуется.

## Оценка → предложение → решение клиента

Новая заявка — запрос оценки, а не подтверждённый заказ. Актуальные этапы: `received` → `processing` → `quoted` → `accepted`. Клиент может вместо согласия выбрать `discussion`, после чего менеджер публикует уточнённое предложение. `cancelled` закрывает оценку. Старые `confirmed`/`completed` остаются только в архивных данных; новые кнопки их не выставляют.

В группе администратор нажимает «Взять на оценку», затем «Назвать цену». Бот адресно запрашивает ответ: первая строка — сумма в BYN (например `150` или `150,50`), следующие строки — что включено и условия (до 600 символов). Цена хранится целым числом копеек. Ответ принимается только на зарегистрированный запрос цены, от администратора группы и для актуальной версии заявки. Изменить цену можно до принятия клиентом.

Клиент видит сумму и условия в приложении. «Подходит, согласовать» принимает стоимость, но не означает выполнение работ или бронирование времени. «Уточнить условия» позволяет отправить необязательный вопрос; менеджеру приходит уведомление, и заявка остаётся в работе. После принятия стоимости менеджер согласовывает время и детали. Бот пытается отправить клиенту личное уведомление о готовой цене со ссылкой в приложение. Если оно недоступно, предложение всё равно сохранено, а группа получает предупреждение.

`POST /api/orders/list` с JSON `{initData,cursor?}` возвращает страницу до 100 заявок текущего пользователя по убыванию `(created_at,id)` и `nextCursor`. Следующую страницу передавать с этим курсором. Список включает заявки с неизвестной доставкой и неудачными попытками; они отображаются отдельно от подтверждённой доставки. Удалённые записи исключаются. `POST /api/orders/get` с `{initData,id}` или `{initData,requestId}` возвращает одну принадлежащую пользователю запись, в том числе старую заявку по глубокой ссылке. `POST /api/orders/decision` принимает `{initData,id,version,action,actionId,note}`, где action — `accept` или `discuss`; действие проверяется по владельцу и версии предложения. Изменение цены и согласие клиента защищены от гонок, дубликатов и принятия старой цены. В интерфейсе список обновляется примерно каждые 10 секунд, а при загрузке многих страниц интервал увеличивается; ввод вопроса не перерисовывается во время набора.

Управление работает через защищённый `/telegram/webhook`. Проверяются секрет webhook, группа, ID сообщения, администратор и версия кнопки. Бот должен иметь возможность проверять администраторов через `getChatMember`.

После миграций и публикации Worker запустить `python3 backend/tools/enable_statuses.py` из корня проекта. Скрипт генерирует секреты для webhook и настройки, передаёт их в Cloudflare через stdin и обновляет кнопки старых сообщений. Токен бота не считывается. Чужой webhook не заменяется. `MINI_APP_URL` задаёт адрес приложения для кнопки web_app в личном уведомлении; параметр order открывает нужную оценку после проверки владельца. `BOT_USERNAME` используется для запасной ссылки startapp. При смене бота обновить BOT_USERNAME и секрет BOT_TOKEN.

## Контакт Telegram и адреса

Имя берётся из проверенных Telegram initData. `requestContact` в мини-аппе открывает системный запрос согласия, но сам номер передаётся боту отдельным `message.contact`. Webhook принимает сообщения и callback_query; контакт сохраняется только из личного чата, если `contact.user_id`, отправитель и ID чата совпадают. `POST /api/contact` с `{initData}` возвращает номер только его владельцу. Миграция `0003_contacts.sql` добавляет контакты и переносит номер из последней успешно отправленной заявки. Подтверждённый номер и вручную введённый номер после успешного заказа подставляются в следующих заказах. При отказе или задержке Telegram доступен ручной ввод без автоматического открытия клавиатуры.

Адреса погрузки и выгрузки показаны рядом, перед настройками этажей. Для переезда переход к контакту отключён, пока не заполнены оба адреса; для других услуг достаточно одного.

## Управление списком

Вкладки «Активные / Архив», по 8 карточек с кнопкой «Показать ещё». Действия находятся в меню «⋯» карточки и деталей: повторить оценку, архивировать, восстановить, отменить текущую оценку или удалить из личного списка. Локальные черновики управляются без запроса API.

`POST /api/orders/organize` принимает `{initData,id,action,version}`. `archive`, `restore`, `delete` меняют только `customer_visibility`, не бизнес-статус. Удаление из списка — скрытие у клиента, а не уничтожение записи у менеджера. Архив и удаление синхронизируются между устройствами и не отменяют оценку. В течение 6 секунд последнюю операцию можно отменить кнопкой в уведомлении. Отдельное действие `cancel` проверяет версию, переводит оценку в cancelled, архивирует её и уведомляет менеджера; повтор не дублирует уведомление. Даже последующее изменение статуса менеджером не возвращает удалённую из списка запись. Миграция `0005_order_organization.sql` создаёт поле видимости и отправляет старые закрытые заявки в архив.

## Повторные попытки и ограничения

- Фото уменьшаются в приложении до длинной стороны 1600 px и JPEG; максимум 2 МБ на фото, 5 фото, 12 МБ на весь HTTP-запрос. Оригиналы на backend не сохраняются.
- После выбора в галерее показываются этап подготовки, счётчик обработанных фото, прогресс и кнопка "Отменить". Готовые миниатюры появляются по очереди. Отмена или возврат назад сохраняют уже подготовленные фото; завершившаяся позже старая обработка не меняет новую форму. Чтение и кодирование ограничены таймаутами. Фото передаются на backend вместе с заявкой при её отправке, а не при выборе в галерее.
- D1 хранит текст заявки, контакты, ID Telegram-пользователя, статус и Telegram file_id. Перед реальным запуском определить срок хранения и актуализировать политику обработки данных заказчика.
- Черновики формы сохраняются в браузере; сами фото остаются только до перезагрузки приложения. При возобновлении черновика после перезагрузки их нужно выбрать заново.
- При явном отказе Telegram повтор безопасен: отправляется только недоставленная часть. При потере ответа Telegram невозможно гарантировать, что сообщение не было доставлено. Такие заявки переходят в `uncertain` (или остаются `sending_*`, если Worker прерван) и требуют проверки группы; автоматический повтор блокируется. Это сознательная защита от дубликатов, а не обещание exactly-once.
- В интерфейсе показывается лишь подтверждённая доставка. «Отправлена» не означает, что менеджер уже прочитал заявку.
- Лимит: 10 новых заявок на пользователя за час. Дополнительно ограничены запросы API (120/мин на пользователя), загрузки (30/мин), попытки доставки (20/час на пользователя, 5 на заявку, пауза минимум 10 секунд), общий входящий поток (1200/мин) и поток с одного IP Cloudflare (180/мин). Общие обращения к Telegram — 300/мин, отправки — 60/мин. Счётчики атомарные в D1; просроченные строки очищаются по расписанию. API не принимает произвольные chat_id от клиента. Не включать логирование тела запросов и токенов.

## Перенос

Контракт интерфейса — multipart POST с заголовком `X-Telegram-Init-Data`, полями `initData`, `requestId`, JSON-полем `order` и повторяющимся полем `photos`. Подпись проверяется до чтения тела; значение в форме должно совпадать с заголовком. Заголовок необходимо разрешить в CORS. Старый клиент без заголовка должен быть обновлён. В ответе успеха: `{ok:true,id,photoCount}`. Для другого хостинга сохраняем этот контракт и проверку Telegram, заменяем D1-адаптер обычной SQL-базой и меняем только `apiBase`. Внешний вид приложения переделывать не нужно.

### Фото и заявка в одной карточке

Новые заявки с фото используют `sendPhoto` для основной карточки: первый снимок, подпись заявки и кнопки управления. Её `message_id` сохраняется в D1. Остальные снимки отправляются ответом на карточку: один через `sendPhoto`, несколько через `sendMediaGroup`. Первое фото не дублируется. При подтверждённом отказе повторяются только оставшиеся снимки; при неоднозначном ответе доставка требует сверки. Статусы и цена обновляют подпись основной карточки через `editMessageCaption`; старые текстовые карточки продолжают использовать `editMessageText`. Кнопка "Полная заявка" появляется только если текущая подпись под фото сокращена до лимита Telegram; при обновлении статуса или цены её видимость пересчитывается.

Выбор времени: `slot=0` – любое время, `1` – 8:00–12:00, `2` – 12:00–17:00, `3` – 17:00–21:00, `4` – своё время. Для `slot=4` обязательны дата и `customTimeFrom` в формате `HH:mm`; `customTimeTo` передаётся пустой строкой или временем позже начала в тот же день. Интервал сохраняется в JSON заявки, виден клиенту и менеджеру. Для стандартных вариантов скрытые поля своего времени сервер не сохраняет. Миграция не требуется.

Подпись укладывается в 1024 символа с явным многоточием у сокращённых строк. Полные данные остаются в D1; администратор группы может раскрыть их кнопкой «Полная заявка» (ответ появляется только по нажатию). Старые сообщения не пересылаются, незавершённые отправки прежнего формата продолжаются с сохранённого этапа.

## Обновление безопасности: миграция 0008

Перед публикацией нового Worker применить все миграции (`npm run migrate` из `backend/`), затем опубликовать Worker и обновлённые статические файлы. Новому коду нужны таблицы `request_limits`, `delivery_outbox`, `delivery_resolutions` и новые поля заявки/контакта. В конфигурации включён Cron раз в минуту: это необходимая часть повторной доставки уведомлений. После обновления открыть мини-приложение заново: старый код без заголовка аутентификации больше не отправляет фото. Команда `wrangler deploy --dry-run` проверяет сборку и ничего не публикует.

Принятие предложения, вопрос клиента, отмена и уведомление о новой цене создают задачи доставки в одной транзакции с событием. Уведомления и изменения карточек повторяются отдельно, с задержкой и учётом `retry_after`. После 10 неудачных попыток или отказа 403 задача требует вмешательства (`failed`). При потере ответа Telegram или завершении процесса во время отправки уведомление переходит в `uncertain` и автоматически не дублируется. Редактирование карточки можно безопасно повторять. Каждая задача защищена атомарной арендой; одновременно выполняется одна задача на заявку. Сбой уведомления не отменяет сохранённое решение клиента.

После явного отказа Telegram можно исправить недоставленную заявку и повторить с прежним `requestId`: сервер меняет данные только в `received`, если сообщения ещё нет. Лимит попыток при редактировании сохраняется. При `sending_*`/`uncertain` менять данные или автоматически создавать новый ID нельзя. Клиент пытается получить сохранённый статус по `requestId` и показывает «Проверяем доставку». При ручном разрешении повтора пользователь видит кнопку для исправления той же заявки; утраченные после перезагрузки фото нужно выбрать заново.

Для сверки зависших доставок запустить из корня `python3 backend/tools/enable_statuses.py --review`. Помощник использует существующий профиль Cloudflare, обновляет секреты и конфигурацию webhook тем же способом, что и обычная настройка, затем показывает записи для проверки. Бот-токен не считывается. Сначала проверить реальную группу; затем указать, доставлено сообщение или точно отсутствует. Для найденной карточки нужен ID её первого сообщения. Требуются пояснение и повтор полного ID записи. Активную отправку нельзя разрешать до завершения двухминутной аренды. Результат сохраняется в `delivery_resolutions`. Ответ «не доставлено» разрешает повтор и безопасен только после реальной сверки группы.

Служебные действия `deliveries`, `resolve_order`, `resolve_notification` доступны только через `/internal/telegram/setup` с `ADMIN_SETUP_SECRET`. Ключ не передавать браузеру, в URL, командной строке или логи. Настройка webhook по-прежнему отказывается заменять чужой обработчик.

Локальные заявки хранятся по ключу `vg-requests-v3:<Telegram ID>:<apiBase>`. Из старого хранилища переносятся только записи с явно совпадающим владельцем; записи без владельца не показываются, а отправленные серверные заявки восстановятся через API. Старый общий ключ удаляется после сохранения. Повтор квитанции не заменяет более новый контакт: телефон заявки сохраняется с временем её создания и источником `order`, а контакт webhook — с источником `telegram`. При одинаковом времени приоритет у Telegram-контакта.

Сервер принимает новые заявки только на услуги `trash`, `construction`, `furniture`, `dem`. Старые заявки других услуг продолжают отображаться. Изменение набора доступных услуг требует согласованного обновления сервера и интерфейса.

## Описание бота, приветствие и чистый личный чат

Миграция `0009_bot_chat.sql` добавляет состояние приветствия и очередь удаления входящих сообщений. После миграции публикуется рабочий Worker. `python3 backend/tools/configure_bot_profile.py --config wrangler.production.jsonc` устанавливает и проверяет полное описание, короткую информацию, команды `/start`, `/help` и кнопку меню. Тексты хранятся в `backend/src/bot-profile.mjs`. Меняется только административный ключ помощника; токен бота не считывается, секрет действующего webhook не меняется.

При `/start`, `/help` или первом обычном обращении в личном чате бот присылает приветствие с кратким объяснением сервиса, затем закрепляет его. Повторные команды обновляют ту же карточку. Если пользователь удалил её, новое сообщение создаётся только после подтверждённого ответа Telegram о том, что прежняя карточка отсутствует. Неоднозначная отправка не повторяется автоматически; повторный явный `/start` или `/help` разрешает восстановление спустя минуту. Сбой закрепления не пересылает приветствие заново.

С миграции `0010_welcome_photo.sql` приветствие поддерживает фото. В рабочей конфигурации `WELCOME_PHOTO_URL` указывает на опубликованную копию изображения из `images/`; имя файла содержит хеш содержимого. Сначала публикуется картинка на GitHub Pages, затем Worker. Существующий текстовый закреп превращается в фото через `editMessageMedia`, сохраняя ID и закрепление. Следующие команды меняют только подпись. Повторное применение `configure_bot_profile.py` обновляет и проверяет существующие приветствия (до 10 за вызов), без отправки новых сообщений; удалённые пользователем карточки при этом не восстанавливаются. При ожидающих или неподтверждённых обновлениях помощник сообщает об этом.

В приветствии больше нет отдельной inline-кнопки. Единственная постоянная кнопка «Получить оценку» остаётся внизу чата; короткая подпись указывает на неё. Новое фото нужно публиковать под новым именем с хешем и обновлять `WELCOME_PHOTO_URL`, чтобы Telegram не использовал прежнюю картинку из кеша. При изменении текста увеличивается `PROFILE_REVISION`.

В рабочем окружении `CLEAN_PRIVATE_MESSAGES=true`: новые входящие текст, фото, файлы и другие обычные сообщения удаляются после успешного закрепления приветствия. Приветствие направляет пользователя в приложение; техническая фраза об автоматической очистке в нём не отображается. Произвольный текст и вложения не сохраняются и не пересылаются менеджерам. Уведомления о цене, приветствие, платёжные/служебные сообщения и сообщения группы заказов автоматически не удаляются. Собственный контакт по-прежнему удаляется только после сохранения номера; чужие контакты не трогаются.

Очистка ограничена по частоте, не более 100 ожидающих записей на пользователя и 10 000 в очереди. Сохраняются только ID пользователя/сообщения и состояние удаления, без текста и вложений. Ошибки Telegram повторяются по Cron, максимум восемь попыток; ответ 429 учитывается. Уже удалённое сообщение считается обработанным. По ограничениям Telegram сообщения старше 48 часов не удаляются, а кубик в личном чате ждёт 24 часа. Метаданные очереди очищаются спустя 48 часов. Старую историю чатов эта функция не перебирает. Без явного `CLEAN_PRIVATE_MESSAGES=true` обычные сообщения сохраняются.

Изменения после проверки коммуникации: дата и готовый интервал сохраняются в черновик сразу, календарный день и проверка прошедшего времени используют Europe/Minsk. Перед отправкой повторно проверяются дата и контакт; явная устаревшая дата возвращает клиента на шаг адреса и времени. Для сегодняшних интервалов проверяется конец окна, для точного времени – само время.

Вопрос к предложению обязателен, но не отзывает текущую цену: клиент может принять её из состояния `discussion` с актуальной версией. Новая цена по-прежнему требует нового решения клиента. После согласия действие называется "Отменить заявку". Уведомления о цене не содержат сумму; очередь проверяет ревизию и переводит устаревшие задачи в `superseded`, включая ранее сохранённые уведомления.

При `text_sent` API возвращает `remainingPhotoCount`. Клиент открывает отдельный экран досылки и отправляет `photoMode=remaining` с тем же `requestId` и только недостающими файлами. Сервер проверяет владельца, состояние, количество и формат фото; использует сохранённые данные заявки, не меняет ID карточки и не повторяет доставленный снимок. Повтор после неоднозначной доставки запрещён до сверки. Новая миграция не требуется.
