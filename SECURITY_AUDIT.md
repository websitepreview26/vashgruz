Это проверка локального исходного кода: опубликованная версия, реальные секреты, настройки Cloudflare/WAF и права рабочей группы не проверялись. ## Подтверждённые проблемы (до исправлений)

### 1. P1: лимит новых заявок не ограничивает повторные попытки и обращения к Telegram

Места: `backend/src/worker.mjs:119–146`, `backend/src/worker.mjs:200–209`; `backend/src/statuses.mjs:56–72`, `backend/src/statuses.mjs:156–179`.

Ограничение 10/час действует при создании новой строки. После явного отказа Telegram строка возвращается в `received`. Следующий запрос с тем же `requestId` снова вызывает отправку, минуя ограничение новых строк. Проверка фото распознаёт только начальные байты, поэтому прохождение серверной проверки не гарантирует, что Telegram примет изображение.

Локальное воспроизведение: 20 последовательных попыток одной заявки при имитации ответа Telegram 400 дали 20 обращений к Telegram, 20 ответов API 502 и всего одну строку в БД. Это обход ограничения **числа попыток**, а не доказательство доставки 20 сообщений.

У `/list`, `/contact`, `/decision`, `/organize` также нет прикладного ограничения частоты запросов. В частности, `contact.diagnostic` позволяет при каждом обращении выполнять запись в БД. Нужны ограничения запросов и попыток доставки по пользователю, задержка повторов, учёт ответа Telegram и общий бюджет обращений к боту. Для нескольких аккаунтов лимит 10 новых заявок на аккаунт сам по себе не предотвращает спам в группе. Внешние ограничения Cloudflare могут уменьшать риск, но их наличие в этом аудите не установлено.

### 2. P1: сохранённые отправленные заявки не изолированы по аккаунту

Места: `index.html:330–346`, `index.html:415–422`, `index.html:457–475`.

Все заявки лежат под общим ключом `vg-requests-v2`. Фильтрация по `ownerId` применяется к черновикам, но все записи `status === 'sent'` сохраняются и доступны для отображения. Очистка происходит только после успешного ответа `/list`.

Воспроизведение: при текущем Telegram ID 42 в хранилище оставлена отправленная заявка с `ownerId: '99'`. Её адрес показывается в списке и остаётся там после ошибки синхронизации. Условие риска — общий браузерный профиль/хранилище при смене аккаунта; API при этом чужую заявку не выдаёт.

Исправление: отдельный ключ хранилища для пользователя и API/бота; обязательная проверка владельца перед отображением всех типов записей. Записи без владельца переносить осторожно, не показывая их автоматически любому аккаунту.

### 3. P2: принятие цены сохраняется, но уведомление менеджеру может потеряться навсегда

Места: `backend/src/statuses.mjs:97–103`, `backend/src/statuses.mjs:135–152`; аналогичная проблема у отмены в строках 165–172.

Сначала фиксируются статус и событие, затем выполняются редактирование карточки и отправка уведомления. Ошибки отправки подавляются. Повтор с тем же `actionId` видит уже существующее событие и не пытается доставить уведомление снова. Если одновременно не обновилась карточка Telegram, группа может вообще не увидеть принятие стоимости. В приложении статус уже успешный.

Воспроизведение: ответ Telegram 429 на уведомление; API возвращает 200 и `accepted`. Повтор действия возвращает 200 без новых попыток уведомить.

Исправление: сохранять задачу уведомления в одной транзакции с изменением статуса, отдельно учитывать доставку и выполнять контролируемые повторы. Не откатывать принятое клиентом решение только из-за сбоя уведомления. Для неоднозначного ответа Telegram нужна отдельная политика сверки, чтобы не обещать невозможную гарантию отсутствия дубликатов.

### 4. P2: редактирование после неудачной отправки заводит форму в тупик

Места: `index.html:636–655`, `index.html:738–742`; `backend/src/worker.mjs:200–210`.

До отправки форма получает `submitId`, а сервер сохраняет отпечаток данных даже при последующем явном отказе Telegram. После ошибки пользователь может вернуться и изменить адрес или фото, но `submitId` остаётся прежним. Сервер отвечает `409 CHANGED`. Повторное нажатие не помогает, поскольку интерфейс снова использует этот ID.

Воспроизведение подтверждено отдельно в клиенте и Worker: первая попытка — 502, исправленный адрес с тем же ID — 409, новой отправки Telegram нет.

Исправление: различать явный отказ, неизвестную доставку и конфликт данных. При доказанном отсутствии доставки разрешать безопасное обновление заявки либо создавать новую попытку с явной связью с предыдущей. При неизвестной доставке автоматически менять ID нельзя: это создаёт риск дубликата. Интерфейс должен обрабатывать `result.code`, а не только текст ошибки.

### 5. P2: повтор старой заявки перезаписывает недавно сохранённый телефон

Места: `backend/src/worker.mjs:119–120`, `backend/src/worker.mjs:210–211`; `backend/src/statuses.mjs:74–75`, `backend/src/statuses.mjs:184–193`.

Повтор уже отправленной заявки возвращает квитанцию, после чего безусловно вызывает `saveContact` с телефоном этой старой заявки. Таким образом, идемпотентный повтор меняет несвязанные актуальные контактные данные.

Воспроизведение: заявка с номером A → через webhook сохранён собственный контакт B → повтор исходного запроса → в `customer_contacts` снова A.

Исправление: повтор квитанции не должен обновлять контакт. Хранить источник и время изменения контакта; сохранение старой заявки не должно побеждать более новое изменение номера. Ручной номер допускается по текущей логике продукта, но его нельзя считать доказательством владения телефоном.

### 6. P2: отмена клиентом возвращает удалённую из списка заявку

Места: `backend/src/statuses.mjs:159–175`; для сравнения, менеджерский переход сохраняет `deleted` в строке 239.

Клиентская отмена безусловно ставит `customer_visibility='archived'`. Если заявку уже удалили из списка на другом устройстве, старое открытое окно может отменить её с актуальной бизнес-версией: удаление эту версию не меняет. Заявка снова попадает в список.

Воспроизведение: `delete` → список пуст → `cancel` с прежней бизнес-версией → список содержит эту заявку с `archived`.

Исправление: при отмене сохранять `deleted` через условное обновление, как это уже сделано для менеджерского изменения статуса. Изменения видимости и бизнес-статуса должны иметь согласованные правила для нескольких устройств.

### 7. P3: скрытые услуги доступны для заказа через API

Места: `index.html:310–318`, `index.html:357`; `backend/src/worker.mjs:5`, `backend/src/worker.mjs:40`.

`flat`, `office`, `load`, `rig` скрыты в выборе услуги, но разрешены сервером. Прямая заявка на `rig` успешно доставляется в имитацию Telegram.

Если услуги действительно приостановлены, это обход бизнес-ограничения. Если скрытие является только оформлением интерфейса, уязвимости здесь нет. При запрете новых заявок нужен отдельный серверный список доступных услуг; исторические записи должны продолжать отображаться.

### 8. P3: обязательный адрес проверяется до очистки управляющих символов

Место: `backend/src/worker.mjs:35–38`.

Адрес из пяти символов `U+0001` проходит проверку минимальной длины, а затем превращается в пустую строку. Следовательно, через API можно отправить заявку без обязательного адреса. Клиентские кнопки не являются защитой от такого запроса.

Воспроизведение: `validateOrder({...validOrder, addr: '\x01'.repeat(5)}).addr` возвращает пустую строку.

Исправление: сначала очистить и нормализовать строку, затем проверять обязательность и длину. Однострочные поля также стоит нормализовать по переводам строк, чтобы пользовательские значения не имитировали служебные строки карточки Telegram.

## Дополнительные ограничения, установленные по коду

- **Ресурсы до аутентификации.** В `backend/src/worker.mjs:80–87,191` тело multipart целиком читается и разбирается до проверки подписи. Размер ограничен 12 МБ, но частота на уровне приложения не ограничена. Подставить разрешённый `Origin` в обычном HTTP-клиенте несложно: CORS защищает браузерный доступ, а не служит аутентификацией. Поддельная подпись всё равно отклоняется. Приоритет P2, если перед Worker нет соответствующих внешних ограничений. Нужны ограничения на входе; отделение создания заявки от загрузки фото позволило бы раньше проверять пользователя. Нагрузочное воспроизведение не выполнялось.
- **Урезание истории без серверной пагинации.** `backend/src/statuses.mjs:58` возвращает максимум 100 заявок, а `index.html:457–462` заменяет ими отправленную локальную историю. Кнопка «Показать ещё» показывает лишь уже полученные записи и не запрашивает следующие страницы. При накоплении истории старые заявки перестанут быть доступны через обычный список. Приоритет P2; нужен курсор и отдельная загрузка заявки по ID с проверкой владельца. Глубокая ссылка также ищет запись только в полученной сотне. В этом аудите установлено чтением кода, без отдельного теста на 101 запись.
- **Неопределённая доставка требует ручного восстановления.** Блокирование `uncertain`/`sending_*` сознательно описано в README и само по себе защищает от дублей. Однако клиент не получает такие заявки в `/list`, а штатного механизма сверки и завершения их состояния в проверенном коде нет. Нужен рабочий сценарий менеджера для сверки с группой. Автоматический повтор с новым ID здесь небезопасен.

## Что работает в проверенных сценариях

- Подпись Telegram проверяется на сервере; дубли параметров, подмена подписи и просроченные данные отклоняются. Срок годности — 24 часа: валидные `initData` являются повторно используемым удостоверением, а не одноразовым разрешением на заявку.
- Чтение заявок и изменения клиента ограничены `user_id`; подмена ID заявки другим клиентом отклоняется.
- Webhook и служебная настройка защищены отдельными секретами. Управление заявкой проверяет группу, сообщение, администратора и версию.
- Обновление цены и решение клиента используют условные транзакционные изменения; проверенные гонки не принимают новую цену от имени клиента.
- Повтор одного успешно доставленного запроса не отправляет заявку заново; конкурентные отправки с одним ID защищены блокировкой состояния.
- В просмотренном SQL значения передаются параметрами. Проверенные пользовательские текстовые поля экранируются при выводе в HTML. Это не является доказательством отсутствия всех возможных SQL/XSS-проблем.
